# سطوح محصول و تفکیک قابلیت‌ها

> **هیچ قابلیتی حذف نشده است.** خواسته صریح تیم: تخصیص بین سطوح، نه حذف.
> ترتیب اجرا در `09-roadmap.md` جای حذف را می‌گیرد.

## قاعده تفکیک

هر تخصیص از این پنج قاعده بیرون آمده. قابلیت جدید هم با همین‌ها جای می‌گیرد.

1. **می‌خواند، می‌سنجد، می‌خرد ← وب.** صفحه بزرگ، صفحه‌کلید، اعتماد پرداخت، ایندکس گوگل.
2. **مصرف می‌کند، عادت روزانه است، در حرکت است ← موبایل.** پخش پس‌زمینه، قفل صفحه،
   هدفون، بلوتوث خودرو، آفلاین، نوتیفیکیشن.
3. **فایل آپلود می‌کند یا ویرایش سنگین دارد ← وب.** استودیو، پورتال ناشر، پنل‌ها.
4. **به میکروفن یا حسگر نیاز دارد ← موبایل.** ضبط، تعامل صوتی، جستجوی صوتی.
5. **کودک مصرف‌کننده و والد تصمیم‌گیرنده ← دو سطح.** کنترل و خرید در وب، مصرف در موبایل.

**قاعده‌ای که کل معماری فرانت را تعیین می‌کند:** هیچ قابلیتی در سطح API «فقط وب» یا
«فقط موبایل» نیست. بک‌اند همه‌چیز را به هر سه سطح می‌دهد؛ تفکیک فقط در لایه رابط
کاربری و اولویت تجربه است.

### یک دارایی، چهار کاربرد

**ترنسکریپت همگام با زمان** را از روز اول تولید و ذخیره کن. همان یک ساختار داده:

1. دسترس‌پذیری برای ناشنوایان
2. هزاران صفحه متنی ایندکس‌پذیر که هیچ رقیب ایرانی ندارد
3. همگام‌سازی متن و صوت و روشن‌شدن کلمه در حال خوانده‌شدن
4. منبع context برای کتاب‌یار بدون پردازش دوباره کتاب

اگر یک تصمیم فنی زودتر از بقیه گرفته شود، این است.

## کودک: دو کاربر، یک حساب

**کسی که مصرف می‌کند پول نمی‌دهد و کسی که پول می‌دهد مصرف نمی‌کند.**
کل معماری این بخش از همین جمله بیرون می‌آید.

| وظیفه | کاربر | سطح |
|---|---|---|
| کشف محصول و تصمیم خرید | والد | وب (صفحه فرود کودک مستقل و SEO-محور) |
| پرداخت و اشتراک | والد | وب |
| ساخت پروفایل کودک و تعیین سن | والد | وب + موبایل |
| سقف زمان روزانه | والد | وب + موبایل (اعمال سمت اپ تا آفلاین هم کار کند) |
| تأیید یا رد محتوا | والد | وب |
| گزارش هفتگی | والد | وب (نمودار) + موبایل (خلاصه). مهم‌ترین ابزار نگهداشت والد |
| انتخاب و پخش قصه | کودک | اپ کودک |
| قصه شب با تایمر | کودک | اپ کودک، صفحه اول |
| پخش آفلاین در خودرو | کودک | اپ کودک. دانلود خودکار روی وای‌فای، تنظیم والد |
| دستاورد و استیکر | کودک | اپ کودک، بدون رقابت با غریبه |
| خروج از حالت کودک | والد | قفل PIN |

### چهار قاعده‌ای که نباید شکسته شود

1. هیچ تبلیغی، در هیچ شکلی.
2. هیچ ورودی متن آزاد به هوش مصنوعی؛ فقط پرسش‌های از پیش تعریف‌شده.
3. هیچ محتوای تولیدشده توسط غریبه در دسترس کودک نباشد.
4. هیچ نوتیفیکیشنی به دستگاه کودک نرود؛ همه به گوشی والد.

**این چهار باید در بک‌اند policy باشند نه شرط در فرانت.** اگر در فرانت باشند،
روزی یکی از سه کلاینت فراموشش می‌کند.

## معماری سوپر‌اپ

هدف: بزرگسال، کودک و خالق محتوا مانند اسنپ‌فود و اسنپ‌پی درون یک اپ جامع.

### چه چیزی از الگوی اسنپ منتقل می‌شود

| الگو | مناسب؟ | دلیل |
|---|---|---|
| یک حساب و یک کیف پول مشترک | **بله** | مهم‌ترین بخش. والد نباید حساب دوم بسازد |
| رجیستری سرویس سمت سرور | **بله** | روشن و خاموش کردن سرویس بدون آپدیت اپ |
| انتشار سرویس‌ها به‌عنوان اپ مستقل | **بله** | اسنپ‌فود هم داخل اسنپ است هم مستقل |
| گرید سرویس‌ها در خانه | محدود | اسنپ ده‌ها سرویس دارد، تو سه تا |
| سرویس‌های کاملاً بی‌ربط | **خیر** | سرویس‌های تو یک کسب‌وکارند با سه مخاطب |
| ران‌تایم مینی‌اپ | **خیر** | برای اکوسیستم توسعه‌دهنده ثالث ساخته می‌شود |

**تفاوت بنیادی:** سرویس‌های اسنپ کارهای متفاوت برای یک نفرند. سرویس‌های کتاپاد
یک کار واحد برای افراد و نقش‌های متفاوت. پس معماری درست «پوسته + ماژول سرویس» است،
نه «پلتفرم مینی‌اپ». این بخش بزرگی از هزینه را حذف می‌کند و تقریباً تمام منفعت را نگه می‌دارد.

### سه لایه

| لایه | محتوا |
|---|---|
| پوسته | اسپلش، ورود OTP، سوییچ پروفایل، کیف پول، پشتیبانی، نوتیف، مسیریاب deep-link، رجیستری سرویس، feature flag، موتور تم |
| سرویس‌ها | `service_listen`، `service_kids`، `service_studio`. بعداً `service_org` و `service_live` |
| قابلیت‌های مشترک | `core_audio`، `core_catalog`، `core_wallet`، `core_sync`، `core_design`، `core_network` |

### ساختار مونوریپو (Melos)

```
ketapod/
  apps/
    ketapod/           سوپر‌اپ، همه سرویس‌ها را ثبت می‌کند
    ketapod_kids/      مستقل، فقط service_kids
  packages/
    core_shell/        میزبان ناوبری . رجیستری سرویس . DI . session
    core_network/      کلاینت تولیدشده OpenAPI . interceptor . retry
    core_auth/         otp . token . profile . role
    core_audio/        تنها موتور صوت — هشدار پایین
    core_catalog/      book . edition . chapter . transcript
    core_wallet/       موجودی . خرید . بررسی entitlement
    core_sync/         موقعیت . صف آفلاین . مدیر دانلود
    core_design/       توکن . تم . ویجت مشترک
    service_listen/    تجربه بزرگسال
    service_kids/      تجربه کودک
    service_studio/    تجربه سازنده (WebView + پل بومی)
```

اپ مستقل «کتاپاد کودک» فقط یک ورودی دیگر در `apps/` است که تنها `service_kids` را
ثبت می‌کند. یک کدبیس، دو خروجی، دو لیست در کافه‌بازار.

### قرارداد ماژول سرویس

```dart
abstract class ServiceModule {
  String get id;                      // "listen" | "kids" | "studio"
  String get titleKey;
  IconData get icon;
  ThemeData themeFor(Brightness b);   // تم مخصوص سرویس
  List<RouteBase> routes();           // زیر /{id}/... سوار می‌شود
  bool isAvailable(SessionContext c); // نقش، نوع پروفایل، flag
  Future<void> warmUp();              // lazy، هنگام اولین ورود
}
```

مسیرها: `/listen/book/123`، `/kids/story/45`، `/studio/upload`.
**متادیتا زودهنگام، کد دیرهنگام** ــ در راه‌اندازی فقط شناسه و آیکون و شرط دسترسی
خوانده شود، وگرنه cold start با هر سرویس جدید بدتر می‌شود.

`minAppVersion` در ایران اهمیت مضاعف دارد چون کاربر کافه‌بازار دیر آپدیت می‌کند.

### ورود به سرویس: پروفایل، نه گرید

اسنپ گرید می‌گذارد چون سرویس‌هایش **کار** هستند. سرویس‌های تو بیشتر **آدم** هستند:

- اجرای اول پس از ورود: «چه کسی گوش می‌دهد؟»
- پروفایل کودک ← مستقیم `service_kids`
- پروفایل بزرگسال ← `service_listen`
- **استودیو** یک نقش است نه شخص؛ کاشی در حساب کاربری، فقط برای نقش `creator`

### دو هشدار

**موتور صوت باید در پوسته باشد، نه داخل سرویس‌ها.** روی هر دستگاه فقط **یک**
audio session و یک نوتیفیکیشن پخش ممکن است. اگر `service_listen` و `service_kids`
هرکدام نمونه `just_audio` خودشان را بسازند: دو کنترل روی قفل صفحه، جنگ بر سر
audio focus، پخش هم‌زمان دو فایل. `core_audio` singleton در پوسته؛ سرویس‌ها فقط
**صف پخش** می‌دهند.

**ایمنی کودک در پوسته اعمال شود.** اگر حالت کودک فقط یک مسیر در مسیریاب باشد،
یک deep-link به `/listen/...` دورش می‌زند. پوسته `SessionMode` نگه دارد، مسیریاب
مسیر خارج از سرویس فعال را رد کند، و `core_network` هدر `X-Profile-Id` بفرستد تا
**بک‌اند هم** سیاست را مستقل اعمال کند.

### استودیو به‌صورت WebView

`service_studio` یک WebView سخت‌شده روی استودیوی وب باشد، به‌علاوه پل بومی برای
دو کار که وب نمی‌تواند: **ضبط با میکروفن** و **آپلود فایل حجیم در پس‌زمینه**.
توکن با one-time code از پوسته پاس داده شود، نه اشتراک‌گذاری cookie.

### تله‌های این الگو

| تله | راه اجتناب |
|---|---|
| حجم اپ | `--split-per-abi`، دارایی سنگین از شبکه نه بسته نصبی |
| زمان راه‌اندازی | ماژول‌ها lazy؛ در راه‌اندازی فقط متادیتا |
| نشت وابستگی بین سرویس‌ها | هیچ سرویسی سرویس دیگر را import نکند. مشترک ← `core_*`. در CI با بررسی گراف وابستگی اجباری کن |
| واگرایی تم | تم هر سرویس از توکن‌های `core_design` مشتق شود |
| ساختن ران‌تایم مینی‌اپ | وسوسه «پلتفرم» شدن را کنار بگذار |
